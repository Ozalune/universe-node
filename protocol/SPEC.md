# Universe Node — Shared Reality Protocol

**Version:** 0.1
**Status:** Initial draft / proof of concept

---

## 0. What this document is

This file is **not code**. It doesn't run anywhere.

It is the **specification** — the set of rules that any implementation
(a Node or a Client, in any language) must follow in order to
participate in the same shared reality.

If two different programs, written by different people, in different
languages, follow this document correctly, they can talk about the
**same universe** and agree on what exists in it.

---

## 1. Fundamental principle

> The universe is the reality.
> The protocol is the language through which that reality is described and modified.
> The Node is the machine that maintains and participates in that reality.
> The client is a window through which someone observes and tries to act upon it.

The protocol has no knowledge of games, genres, or fiction types. It
only knows: **Entity, Property, Relation, Action, Event, Rule, State.**

---

## 2. Physical Substrate vs. Narrative Layer

This is the rule that allows a shared universe to sustain, at the same
time, a science-fiction client and a magic/fantasy client — without
one invalidating the other, and without the protocol needing to know
what "magic" or "science" even is.

### 2.1 The Physical Substrate (mandatory, generic)

Every Event that changes the State must be expressible in **generic
physical/mechanical terms** — things like: energy release, matter
transfer, property change, Entity creation/destruction, Relation
change.

These are the universe's `Rules`. They have no opinion on *why*
something happened — only on **what changes and under which
conditions the change is allowed**.

Example Rule (conceptual):

```
Rule: energy_release
  If an Event of type "region.energy_release" occurs with magnitude M
  within a radius R from a point:
    - every Entity inside radius R whose "structural_integrity"
      property is lower than M loses its "exists_in" Relation to its
      current region (i.e.: it is destroyed/removed from the State)
    - the affected region has its "energy_signature" property changed
```

This Rule is **genre-blind**. It has no idea whether the energy came
from a stellar explosion or from a spell.

### 2.2 The Narrative Layer (optional, free-form, non-normative)

Every Event may carry an optional `narrative` (or `narrative_origin`)
field — free text, defined by the client that generated the action,
describing **how that event is interpreted** within that client's
genre/fiction.

```json
{
  "id": "event_5521",
  "type": "region.energy_release",
  "actor": "player_042",
  "target": "region_star_0001",
  "data": { "magnitude": 9.8, "radius": 40 },
  "narrative": "supernova_trigger"
}
```

The same type of Event, generated by a magic client, could carry
`"narrative": "meteor_spell"` — **same physical Rule, same real
consequence on the State, different story.**

**Golden rule:** the `narrative` field can NEVER be used by a Node to
decide whether an Action is valid, or what an Event does to the State.
It is presentation-only. A Node that completely ignores every
`narrative` field in the universe must still produce a State identical
to a Node that displays them.

This same principle extends to timing, not just content: a client may
choose to *delay how it reveals* an already-settled Event to its
player (for example, narrating that "signals take time to travel
across the universe"). That delay is a presentation choice made by the
client — the Event itself already happened, with a real timestamp and
sequence, at the moment the Node accepted it. The protocol has no
concept of narrated transmission delay; see section 10 for how a
client may use this pattern.

### 2.3 Breaking the rules is also ruled

A universe may allow Events that violate "normal" physical behavior
(altering causality, reversing time, etc.) — but this isn't an
informal exception, it's **a special, explicit Rule**, with its own
conditions and its own cost. When that Rule is triggered, it produces
an Event of a recognizable anomaly type (e.g.
`"type": "anomaly.created"`), which becomes a **permanent fact of the
universe**, visible to any client — not a hidden local effect inside
one app.

In other words: there's no "cheating physics for free." Every
violation becomes a shared, recorded piece of history.

---

## 3. One universe, not a multiverse (for now)

v0.1 assumes a **single Universe** with one identity, one seed, and one
set of Rules. Multiple independent universes (a multiverse) may emerge
in the future as a natural consequence (different seeds/rulesets), but
this is not modeled as a first-class concept yet.

## 4. Protocol entities

### 4.1 Universe

Represents the reality itself.

```json
{
  "id": "universe_asterion",
  "name": "Asterion",
  "seed": "928374928",
  "protocol_version": "0.1",
  "ruleset": "core-0.1",
  "created_at": "2026-01-01T00:00:00Z"
}
```

### 4.2 Entity

Something that exists in the universe. The protocol doesn't need to
know (and shouldn't need to know) what a specific `type` "means"
narratively.

```json
{
  "id": "planet_0001",
  "type": "planet",
  "name": "World A",
  "created_at_event": "event_0007"
}
```

### 4.3 Property

An attribute of an Entity. Modeled as a separate fact (not embedded
directly in the Entity) so that Property changes are themselves
traceable as Events.

```json
{
  "entity": "planet_0001",
  "property": "gravity",
  "value": 0.91
}
```

### 4.4 Relation

A link between two Entities.

```json
{
  "from": "planet_0001",
  "relation": "orbiting",
  "to": "star_0001"
}
```

### 4.5 Action (intent — NOT reality)

What an actor (player, system, another Node) **requests** to happen.

```json
{
  "actor": "player_001",
  "type": "land",
  "target": "planet_0001",
  "data": {},
  "narrative": "optional, free-form"
}
```

An Action never changes the State directly. It is submitted to the
Validator.

### 4.6 Event (accepted fact)

The result of a successfully validated Action. Events are immutable
and ordered — together, they form the universe's history.

```json
{
  "id": "event_0007",
  "sequence": 7,
  "timestamp": "2026-01-01T00:03:12Z",
  "type": "player.landed",
  "actor": "player_001",
  "target": "planet_0001",
  "data": {},
  "narrative": "optional, free-form"
}
```

### 4.7 Rule

A validation condition and/or effect on the State, associated with one
or more Action/Event `type`s. In v0.1, Rules can be implemented
directly in code (a validation function), as long as they're
documented in `protocol/schemas/` in a readable way.

### 4.8 State

Not a separately stored entity — it is the result of applying, in
order, all accepted Events on top of the base Universe generated from
the seed.

```
SEED + RULES + EVENTS = CURRENT STATE
```

Two Nodes with the same seed, the same ruleset, and the same sequence
of Events **must** arrive at the same State.

---

## 5. Mandatory flow: Action ≠ Event

```
ACTION → VALIDATION → EVENT → STATE CHANGE
```

No Action changes the State directly. A Node receiving an Action must:

1. Check the Rules applicable to the Action's `type`.
2. If valid: create the corresponding Event, persist it, apply it to
   the State, and return confirmation (`accepted: true`, `event_id`).
3. If invalid: reject without creating an Event or changing the State
   (`accepted: false`, reason — see section 9 for how rejection
   reasons should be given context, not just a flat "no").

---

## 6. Determinism

Given:

```
seed = X
ruleset = Y
```

any correct implementation of the protocol must generate the **same
base Universe** (same initial Entities, Properties, Relations) before
any Event is applied. This allows Nodes to reconstruct parts of
reality without needing to transfer the entire history.

The generation algorithm used in v0.1 (a seed-based deterministic
PRNG, keyed by seed + coordinates) is documented in
`protocol/schemas/` and must be followed exactly by any implementation
that wants to generate the same base Universe.

---

## 7. Player identity as a fact of the universe

The protocol does not define accounts, passwords, or login. Identity
is handled the same way everything else is: **as an Event.**

The first time a given `actor` id submits any Action to a Node, the
Node produces an Event marking that actor's entry into the universe —
for example:

```json
{
  "id": "event_0002",
  "sequence": 2,
  "timestamp": "2026-01-01T00:01:00Z",
  "type": "player.joined",
  "actor": "player_001",
  "target": null,
  "data": { "entry_coordinates": [12, -88, 4] }
}
```

This is not a side effect of some separate "registration" system —
it's the same Action → Validation → Event flow as everything else in
section 5. There is no username/password, no server-side account
table. An actor id simply becomes real the moment it is first used,
and that moment is permanently recorded like any other fact of the
universe.

This means an actor's identity is only as unique as the id string it
uses. The protocol doesn't currently prevent two different people from
choosing the same actor id (see section 11 — cryptographic identity is
future work). For v0.1, a client is expected to generate a random,
sufficiently unique actor id locally on first launch and reuse it
afterward, rather than letting people type in an arbitrary name that
could collide with someone else's.

## 8. Spatial locality — clients ask for what's near them

Because the universe is effectively unbounded (see section 6 —
anything can be generated on demand from seed + coordinates), a
client must never ask a Node for "everything that exists." Instead, a
client asks for what's near a given point:

```
"what exists within radius R of coordinates (x, y, z)?"
```

The Node answers only with Entities and Events relevant to that
region — generating any not-yet-touched base Entities on the fly
(section 6), and including only the actual recorded Events tied to
that area. This keeps both computation and data transfer proportional
to where a player actually is, not to the size of the universe.

This is a requirement on how Nodes expose data (i.e., on the future
local/network API), not a new data structure — it doesn't change
anything in section 4.

---

## 9. Conflicting actions — first accepted, clearly explained

Because a Node processes Actions one at a time (see section 6 of the
main flow), there is never ambiguity about *which* Action was accepted
first when two actors target the same thing — whoever's Action the
Node processes first wins, and it becomes the Event of record.

What matters is that the loser is told *why*, with enough context to
make sense of it — not just a bare rejection:

```json
{
  "accepted": false,
  "reason": "coordinate already claimed",
  "conflicting_event": "event_0089",
  "claimed_by": "player_004"
}
```

A client can use this to tell a meaningful story to its player ("someone
else got here first") instead of showing a generic error. This is a
convention for how rejections should be shaped, not a new entity type.

---

## 10. Narrative artifacts (e.g., messages left in the world)

Not every visit to a place needs to become a permanent Event — merely
passing through and doing nothing is not required to leave a trace.
But a player may choose to perform a deliberate action that *does*
leave one, such as leaving a written message at a location:

```json
{
  "actor": "player_001",
  "type": "leave_message",
  "target": "planet_0001",
  "data": { "text": "Nothing but ice here. Don't bother." }
}
```

Once validated, this becomes a normal Event like any other, tied to
that Entity/coordinate, and any client visiting that same place later
can retrieve and display it (subject to the spatial locality rule in
section 8 — it's just part of "what's near this location").

This is deliberately the same mechanism as everything else in the
protocol — there is no separate "chat system." A conversation between
players is just a sequence of `leave_message` Events at the same
location, read asynchronously whenever someone visits.

To keep this from growing into unbounded storage, an implementation
should apply a reasonable length limit to free-text `data` fields used
this way (v0.1 suggests around 200–300 characters) — a convention, not
a protocol-level restriction.

Whether a given client treats "visiting" versus "leaving a mark" as
meaningfully different is entirely a narrative/gameplay decision for
that client to make — the protocol only needs to support the latter as
an ordinary Action/Event.

## 11. What this protocol explicitly does NOT define yet (v0.1)

To avoid over-scoping the first version, the items below are mentioned
only as future direction, not as part of this version's normative
content:

- Node-to-Node synchronization
- Distributed consensus / conflict resolution across multiple Nodes
- Cryptographic identity for player/client, separate from the Node's
  (v0.1 identity, per section 7, is just a first-seen actor id)
- Partial snapshots / universe sharding
- Multiverse as a first-class concept
- Detailed physics (v0.1 only ships one minimal example physical Rule,
  just enough to prove the concept in §2)
- Rate limiting / abuse prevention for public-facing Nodes

## 12. Appendix A — Suggested Vocabulary (non-normative)

This section is **not part of the protocol's mandatory rules**. It is
a starting point — a set of suggested Entity `type`s, Properties, and
Relations, meant to reduce fragmentation between different
implementations (e.g., avoiding one client using `gravity` and another
using `grav` for the same thing).

Any implementation is free to ignore, extend, or replace this
vocabulary. What's mandatory is only the generic structure in
sections 4–6 above.

The vocabulary is organized into five content areas, plus two areas
that are not "content" but rather the protocol's own mechanism:

```
Physics       → not an Entity — becomes RULES (mechanism, section 4.7)
Cosmology     → space-scale Entities
Life          → biological/cognitive Entities
Society       → social organization Entities and Relations
Phenomena     → narrative layer + anomalies (sections 2.2 and 2.3)
History       → not an Entity — it's the Event Store (mechanism, section 4.6)
```

### 12.1 Physics (mechanism — Rules, not Entity)

Not Entities. They are Rules that any Entity in the universe can be
subject to, depending on its Properties.

| Suggested Rule | Affects | Relevant example Property |
|---|---|---|
| `gravity` | Entities with mass/position | `mass`, `gravity` |
| `time` / `causality` | Event ordering | `sequence`, `timestamp`, `caused_by` |
| `matter` (`energy_release`) | Entities within a radius | `structural_integrity`, `energy_signature` |

### 12.2 Cosmology

| Suggested `type` | Suggested Properties | Suggested Relations |
|---|---|---|
| `star` | `mass`, `luminosity`, `temperature` | — |
| `planet` | `gravity`, `atmosphere`, `temperature`, `biosphere` | `orbiting → star` |
| `region` / `sector` | `coordinates`, `energy_signature` | `located_in` |

### 12.3 Life

| Suggested `type` | Suggested Properties | Suggested Relations |
|---|---|---|
| `organism` | `species`, `health` | `lives_on → planet` |
| `creature` | `behavior`, `hostility`, `movement_type` | `located_in → region` |
| (intelligence) | `sapience_level` Property on an Entity above, not its own `type` | — |

### 12.4 Society

| Suggested `type` | Suggested Properties | Suggested Relations |
|---|---|---|
| `civilization` | `language`, `tech_level` | `controls → region/planet` |
| `settlement` (city/base) | `population`, `name` | `located_on → planet`, `owned_by → player/civilization` |
| — (economy) | `currency` Property on a civilization | `trades_with → civilization` |
| — (politics) | — | `allied_with`, `at_war_with → civilization` |

### 12.5 Phenomena (narrative layer + anomalies)

Doesn't introduce new physical `type`s. Uses the `narrative` field
(section 2.2) on top of existing Events:

- **magic**, **technology** → same physical Event (e.g.
  `region.energy_release`), different `narrative`
  (`"meteor_spell"`, `"plasma_cannon"`, etc.)
- **anomalies** → Events of type `anomaly.created`, per section 2.3,
  when a special violation Rule is triggered.

### 12.6 History (mechanism — Event Store, not Entity)

Not an Entity or a content category — it's the universe's own Event
log (section 4.6). The entire "history" of the universe is, by
definition, the stored sequence of Events.
